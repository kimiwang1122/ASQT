整体技术架构可以概括为：

**以数据契约、策略契约、订单契约为核心的分层可替换架构。**

主要分层如下：

1. **数据源层**  
   接入 FTShare、baostock、AkShare、Tushare 或商业数据源。  
   这一层只负责拉取原始数据，产物是 `raw_data`，并记录来源、批次、调用成本、授权状态和健康状态。

2. **数据标准与治理层**  
   由 `DataNormalizer` 和 `QualityChecker` 负责。  
   作用是把不同来源的数据统一为标准行情、交易日历、主数据、复权因子、停牌、涨跌停等标准表，并做完整性、合法性、连续性、跨源对账和时点正确性检查。

3. **研究回测层**  
   以 Qlib 作为主要研究和回测主干，但 Qlib 只应被封装在 `ResearchEngine` 内部。

   输出不是直接交易指令，而是 `factor_signal`、回测报告、实验记录等。

4. **策略管理层**  
   `StrategyService` 管理策略版本、参数组、生命周期、风控配置和目标持仓。  
   策略从草稿、候选、模拟盘、暂停、停用到归档都需要状态迁移记录。  
   关键产物是 `strategy_version`、`parameter_set`、`target_position`。

5. **订单与风控层**  
   `OrderService` 把目标持仓转换为标准订单 `standard_order`。  
   这一层负责订单状态机、幂等键、资金约束、仓位限制、涨跌停、停牌、T+1、100 股交易单位、止盈止损、最大回撤等前置检查。  
   这是策略和执行通道之间的关键隔离层。

6. **执行适配层**  
   `ExecutionAdapter` 屏蔽本地模拟盘、QMT/XtQuant、vn.py 或未来其他券商通道的差异。  
   一期先走本地模拟盘 `PaperBroker`，后续再接 QMT/XtQuant 模拟盘，最后才考虑小资金实盘。  
   统一接口包括提交订单、撤单、查询订单、查询资金、查询持仓、接收回报和通道状态检查。

7. **账本、对账与复盘层**  
   账本记录订单、成交、持仓、现金、费用、权益曲线和每日账户快照。  
   `ReviewService` 结合 MLflow、Qlib 报告和自研报表做收益归因、滑点分析、成交率分析、回测与模拟盘偏差分析。  
   目标是能从任一亏损日或异常日反查数据版本、策略版本、订单、成交、费用和风控事件。

8. **运营控制与 UI 层**

   `AlertService` 和 `AuditLog` 负责告警和人工操作留痕。  
   Web 控制台用 FastAPI + 本地前端，页面包括总览、数据、策略、交易、复盘、设置，定位是日常巡检和异常下钻，不是营销页。

我的判断如下。

**Python：适合**
量化系统核心生态基本在 Python：Qlib、pandas、numpy、scikit-learn、MLflow、AkShare、baostock、Tushare、xtquant 适配都更自然。  
所以研究、数据处理、回测、策略、调度脚本、执行适配层，用 Python 是合理的。

**Django：可以用，但偏重**
Django 适合后台管理系统、权限、表单、ORM、Admin、传统业务 Web。  
但你这套系统一期重点不是复杂后台 CRUD，而是：

- 数据管道
- 回测实验
- 策略版本
- 调度任务
- 订单状态机
- 账本对账
- 本地运行和后续云端迁移

这些更像“数据工程 + 任务编排 + API 服务”，不是典型 Django 管理后台。  
所以技术设计文档里选 **FastAPI + 本地前端**，逻辑上更轻，也更贴合服务化接口、异步任务、后续执行网关。

**MySQL：可以用，但我更倾向 PostgreSQL 或 SQLite 起步**
MySQL 不是不能用。它可以承载策略表、订单表、账本表、调度日志、审计记录。

但量化系统会有较多：

- 时间序列数据
- JSON 参数配置
- 实验元数据
- 复杂查询
- 后续指标聚合
- 数据版本追溯

PostgreSQL 在 JSON、窗口函数、分析查询、时间序列扩展生态上通常更舒服。  
一期如果只是 Mac 本地 POC，用 SQLite + Parquet 更低成本；进入服务化后再迁移 PostgreSQL，比一开始上 MySQL 更干净。

我会这样定位：

| 组件 | 是否考虑 | 我的建议 |
|---|---:|---|
| Python | 应该考虑 | 核心语言 |
| Django | 可考虑 | 适合后台管理增强，不建议一期主框架 |
| MySQL | 可考虑 | 可用，但不如 SQLite/Parquet 起步、PostgreSQL 演进自然 |
| FastAPI | 推荐 | 更适合 API、执行网关、轻服务化 |
| PostgreSQL | 推荐中后期 | 更适合版本、账本、实验、分析查询 |
| Parquet | 推荐 | 适合行情、因子、回测中间数据 |

如果后续你明确想要一个“管理后台优先”的系统，比如大量配置页面、权限角色、审批流、表单录入、Admin 后台，那 Django 的价值会上升。  
但按当前三份文档描述，这套系统的主矛盾是 **数据可信、回测可复现、交易链路可追溯**，不是后台管理页面复杂度，所以 Django + MySQL 不应成为默认答案。
